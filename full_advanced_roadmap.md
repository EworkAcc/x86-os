# Full Advanced Roadmap: System Calls and Layered File System for x86-os

This comprehensive roadmap details the implementation of advanced system calls and a sophisticated layered file system architecture for the `x86-os` project. The plan is structured to build foundational components first, progressively adding complexity to achieve a robust and flexible operating system. It emphasizes a modular approach, allowing for independent development and testing of each component.

## Part 1: Advanced System Call Implementation

This section outlines the steps to establish a powerful and secure system call interface, enabling user-space applications to interact effectively with kernel services.

### Phase 1: Basic System Call Mechanism

This foundational phase establishes the core infrastructure for system calls using software interrupts, providing the essential bridge between user and kernel modes.

#### Step 1.1: Choose a System Call Mechanism

*   **Decision**: Initially, `int 0x80` will be used due to its simplicity and broad compatibility with older x86 architectures. This mechanism is well-understood and easier to debug during initial development. Future optimizations can include `sysenter`/`sysexit` for improved performance on modern CPUs.
*   **Action**: Configure the system to use `int 0x80` as the primary software interrupt for system calls.

#### Step 1.2: Define System Call Numbers

*   **Action**: Create a dedicated header file, such as `include/syscall.h`, to enumerate and define unique integer constants for each system call. This ensures a clear and consistent API for both kernel and user-space components. Examples include `SYS_EXIT`, `SYS_WRITE`, and `SYS_READ`.

#### Step 1.3: Modify the Interrupt Descriptor Table (IDT)

*   **File**: The primary modification will occur in `drivers/INTERRUPTS/idt.c` or a similar module responsible for IDT management.
*   **Action**: An entry must be added to the IDT specifically for the chosen system call interrupt vector (e.g., `0x80`). Crucially, the Descriptor Privilege Level (DPL) for this entry must be set to 3. This configuration permits user-mode applications to trigger the system call interrupt, initiating a controlled transition to kernel mode. The entry will point to an assembly-language system call handler.

#### Step 1.4: Create the Assembly System Call Handler

*   **File**: A new assembly file, `kernel/syscall_asm.s`, will house this critical component.
*   **Purpose**: This assembly routine serves as the immediate target of the `int 0x80` instruction. Its responsibilities are paramount for maintaining system stability and security during the mode transition.
*   **Action**: Implement the following sequence:
    1.  **Save User Context**: Preserve the complete user-mode execution environment by pushing all general-purpose registers (`pushad`), segment registers (`push ds`, `push es`), and other relevant CPU state onto the kernel stack. This ensures that the user process can resume execution seamlessly after the system call.
    2.  **Set Up Kernel Segments**: Load appropriate kernel data segment selectors into the `DS` and `ES` registers. This establishes the kernel's own memory context, preventing unauthorized access to user-space memory during kernel execution.
    3.  **Call C Dispatcher**: Transfer control to a C-language system call dispatcher function. The saved register state (typically a pointer to the stack frame containing the registers) is passed as an argument.
    4.  **Restore User Context**: Upon the C dispatcher's return, restore the original segment registers (`pop es`, `pop ds`) and general-purpose registers (`popad`) from the kernel stack.
    5.  **Return to User Mode**: Execute the `iret` (Interrupt Return) instruction. This atomically restores the user-mode `EIP`, `CS`, `EFLAGS`, `ESP`, and `SS` registers, returning control to the user-mode application at the exact point of interruption.

#### Step 1.5: Implement the C System Call Dispatcher

*   **File**: A new C file, `kernel/syscall.c`, will contain the dispatcher logic.
*   **Purpose**: This C function acts as the central hub for system call processing. It receives the saved user-mode register state and, using the system call number (conventionally passed in `EAX`), determines and invokes the appropriate kernel service function.
*   **Action**: Implement a `switch` statement that branches based on the system call number.
    *   Each `case` will correspond to a specific system call (e.g., `SYS_EXIT`, `SYS_WRITE`) and will call its respective kernel service function (e.g., `sys_exit()`, `sys_write()`).
    *   Parameters required by the kernel service functions will be extracted from the saved register state (e.g., `EBX`, `ECX`, `EDX`).
    *   The return value generated by the kernel service function must be placed back into the `EAX` register within the saved register state. This ensures that when `iret` is executed, the user-mode `EAX` register receives the system call's result.

#### Step 1.6: Implement a Basic System Call (e.g., `SYS_WRITE`)

*   **File**: This can be implemented within `kernel/syscall.c` or integrated with existing drivers like `drivers/FB/fb.c` or `drivers/SP/sp.c`.
*   **Purpose**: To provide a simple, verifiable system call that allows for immediate testing of the entire system call mechanism.
*   **Action**: Implement `sys_write(const char *buf, size_t len)`. This function will utilize the existing frame buffer driver or serial port driver to output a string to the console. Successful execution of this system call confirms the basic functionality of the system call infrastructure.

#### Step 1.7: Create a User-Mode Test Program

*   **File**: A new assembly file, `user/test_syscall.s`, or a modification to `user/init.s`.
*   **Purpose**: To thoroughly verify the end-to-end functionality of the system call chain from user-space.
*   **Action**: Develop a small assembly program that:
    1.  Initializes the user-mode stack and segments (if not already handled by `um.s`).
    2.  Loads the `SYS_WRITE` system call number into the `EAX` register.
    3.  Places the memory address of a test string and its length into other general-purpose registers (e.g., `EBX` for buffer address, `ECX` for length).
    4.  Executes the `int 0x80` instruction to trigger the system call.
    5.  Inspects the return value in `EAX` to confirm success or identify errors.
    6.  Calls `SYS_EXIT` to gracefully terminate the user-mode program.

### Phase 2: Advanced System Call Features

This phase focuses on enhancing the system call interface for robustness, security, and efficiency, introducing more complex functionalities required by a modern OS.

#### Step 2.1: Parameter Validation

*   **Action**: Implement rigorous validation checks for all parameters passed from user mode to kernel mode within each kernel service function. This is crucial for security and stability.
    *   **Pointer Validation**: Verify that all user-provided pointers (e.g., `buf` in `sys_write`) point to valid, accessible user-space memory regions. Crucially, prevent any attempts to dereference pointers into kernel memory space.
    *   **Value Validation**: Validate integer and other scalar parameters for valid ranges and conditions (e.g., ensuring `len` in `sys_write` is not excessively large or negative).

#### Step 2.2: Error Handling

*   **Action**: Define a standardized set of error codes (e.g., negative integers corresponding to `errno` values like `-EINVAL`, `-EACCES`, `-ENOMEM`).
*   **Action**: Modify the C dispatcher and all kernel service functions to return the appropriate error code in `EAX` upon failure. This allows user-mode applications to diagnose and handle errors effectively.

#### Step 2.3: Implement Core Memory Management System Calls

*   **Purpose**: Provide user-mode programs with the ability to manage their own memory dynamically, a prerequisite for complex applications and libraries like `malloc()`.
*   **Action**: Implement:
    *   `SYS_SBRK(intptr_t increment)`: Adjusts the program's data segment size. This is a simpler memory allocation mechanism often used in early OS development.
    *   `SYS_MMAP(void *addr, size_t length, int prot, int flags, int fd, off_t offset)`: Maps files or devices into the process's virtual address space. This is a highly complex but powerful system call, requiring deep integration with the paging system and the VFS. It enables demand paging and shared memory.
    *   `SYS_MUNMAP(void *addr, size_t length)`: Unmaps previously mapped memory regions.

#### Step 2.4: Implement Process Management System Calls

*   **Purpose**: Enable the creation, termination, and management of processes, forming the basis of a multi-tasking operating system.
*   **Action**: Implement:
    *   `SYS_FORK()`: Creates a new process that is a duplicate of the calling process. This involves copying the parent's address space (ideally using Copy-on-Write), file descriptors, and CPU state. This is one of the most complex system calls.
    *   `SYS_EXECVE(const char *pathname, char *const argv[], char *const envp[])`: Replaces the current process image with a new program. This requires parsing executable formats (e.g., ELF), setting up a new stack, and loading the new program's code and data into memory.
    *   `SYS_WAITPID(pid_t pid, int *wstatus, int options)`: Waits for a child process to change state (e.g., terminate).
    *   `SYS_EXIT(int status)`: Terminates the calling process.

#### Step 2.5: Implement Inter-Process Communication (IPC) System Calls

*   **Purpose**: Allow processes to communicate and synchronize with each other.
*   **Action**: Implement:
    *   `SYS_PIPE(int pipefd[2])`: Creates a unidirectional data channel (pipe) for inter-process communication.
    *   `SYS_SHMGET(...)`, `SYS_SHMAT(...)`, `SYS_SHMDT(...)`: System calls for shared memory segments, allowing multiple processes to access the same physical memory region.
    *   `SYS_FUTEX(...)`: Fast User-space Mutex. Provides a low-level synchronization primitive that can be used to implement higher-level locking mechanisms (like mutexes and semaphores) efficiently, often avoiding kernel transitions when contention is low.

#### Step 2.6: Consider `sysenter`/`sysexit` (Optional Optimization)

*   **Decision**: If performance is critical and the target CPU supports it, implement `sysenter`/`sysexit` as an alternative, faster system call mechanism. This would involve a separate IDT entry and assembly handler, bypassing the interrupt overhead.

## Part 2: Layered File System Implementation

This section outlines the development of a sophisticated layered file system, inspired by the "Zen of File Systems" [1]. This architecture provides extreme flexibility, allowing for dynamic stacking of functionalities like caching, encryption, and network access.

### Phase 1: Low-Level Disk Access (ATA PIO Driver)

This foundational phase establishes the ability to read and write raw data to a hard disk, which is the base for all file system layers.

#### Step 1.1: ATA PIO Controller Initialization

*   **Purpose**: Detect and initialize the ATA controller (typically IDE) in Programmed I/O (PIO) mode.
*   **Action**: Implement functions to probe for ATA devices (master/slave on primary/secondary channels) via I/O port examination. Configure the controller for PIO data transfers.

#### Step 1.2: Basic Sector Read/Write Functions

*   **File**: `drivers/ATA/ata.c` (new directory and file).
*   **Purpose**: Provide fundamental functions to read and write single 512-byte sectors from/to the disk using Logical Block Addressing (LBA).
*   **Action**: Implement `ata_read_sector(uint32_t lba, uint8_t *buffer)` and `ata_write_sector(uint32_t lba, const uint8_t *buffer)`.
    *   These functions will involve sending commands to ATA command ports (e.g., `0x1F0-0x1F7` for the primary master channel).
    *   Crucially, they must handle status checks (e.g., `DRQ` for data request, `BSY` for busy) and manage 16-bit word data transfers to/from port `0x1F0`.

#### Step 1.3: Multi-Sector Read/Write

*   **Purpose**: Enhance disk I/O performance by enabling the reading and writing of multiple contiguous sectors in a single operation.
*   **Action**: Implement `ata_read_sectors(uint32_t lba, uint8_t count, uint8_t *buffer)` and `ata_write_sectors(uint32_t lba, uint8_t count, const uint8_t *buffer)`.

#### Step 1.4: Error Handling and Retries

*   **Purpose**: Increase the robustness of the disk driver against transient hardware errors.
*   **Action**: Incorporate logic to inspect ATA error registers and implement basic retry mechanisms for failed read/write operations.

## Part 3: Virtual File System (VFS) Layer

The VFS is the cornerstone of a layered file system, providing a unified, abstract interface that decouples applications from the specifics of underlying file system implementations and allows for the stacking of layers.

### Phase 3.1: Define VFS Node and File System Structures

*   **File**: `include/vfs.h` (new file).
*   **Purpose**: Create generic structures to represent file system objects (files, directories) and the file systems themselves.
*   **Action**: Define `struct vfs_node` with common attributes (name, type, size, permissions) and a set of function pointers for standard file operations (e.g., `open`, `close`, `read`, `write`, `seek`, `readdir`). Also, define `struct vfs_filesystem` to represent a registered file system type, including its name and a set of operations it supports (e.g., `mount`, `unmount`, `get_root`).

### Phase 3.2: Implement VFS Core Functions

*   **File**: `kernel/vfs.c` (new file).
*   **Purpose**: Provide the central dispatch mechanism for all file system operations requested by user-space or other kernel components.
*   **Action**: Implement `vfs_open(const char *path, int flags)`, `vfs_read(vfs_node_t *node, void *buffer, size_t size, off_t offset)`, `vfs_write(...)`, `vfs_close(...)`, etc.
    *   These functions will be responsible for parsing file paths, resolving path components, traversing the VFS hierarchy, and dispatching calls to the appropriate underlying file system layer or concrete file system via their respective function pointers.

### Phase 3.3: Mount Points and File System Registration

*   **Purpose**: Enable dynamic mounting of different file systems (including layered ones) at various points within the VFS hierarchy.
*   **Action**: Implement `vfs_mount(const char *path, vfs_filesystem_t *fs_type, void *device_info)` and `vfs_register_filesystem(vfs_filesystem_t *fs_type)`.
    *   `vfs_mount` will associate a specific instance of a file system (e.g., an Ext2 partition) with a VFS path. `vfs_register_filesystem` will add a new file system *type* (e.g., Ext2, FAT, or a custom layered FS) to the VFS.

## Part 4: Concrete Base File System (e.g., Simple Ext2)

This phase involves implementing a fundamental, non-layered file system that interacts directly with the block device driver. A simplified Ext2 is a good choice due to its robustness and feature set, providing a solid base for layering.

### Phase 4.1: Choose and Document Base File System

*   **Decision**: Implement a simplified version of Ext2. This includes support for inodes, directories, and data blocks, but can omit advanced features like journaling or extended attributes initially.
*   **Action**: Thoroughly document the chosen subset of the Ext2 on-disk layout, including superblock, group descriptors, block bitmaps, inode bitmaps, and inode structures [2].

### Phase 4.2: Implement Superblock and Group Descriptor Management

*   **File**: `fs/ext2/ext2_core.c`.
*   **Purpose**: Read, parse, and manage the Ext2 superblock and Block Group Descriptor Table (BGDT).
*   **Action**: Implement functions to:
    *   Read the superblock from a specific disk block, validate its magic number, and extract global file system parameters (block size, inode count, etc.).
    *   Read and interpret the BGDT to locate block bitmaps, inode bitmaps, and inode tables for each block group.

### Phase 4.3: Inode Management

*   **File**: `fs/ext2/ext2_inode.c`.
*   **Purpose**: Handle the allocation, deallocation, reading, and writing of inodes.
*   **Action**: Implement functions for:
    *   `ext2_read_inode(uint32_t inode_num, inode_t *inode_buffer)`: Retrieves an inode's metadata from the inode table on disk.
    *   `ext2_write_inode(uint32_t inode_num, const inode_t *inode_buffer)`: Writes an inode's metadata back to disk.
    *   `ext2_alloc_inode()`: Finds and allocates a free inode using the inode bitmap.
    *   `ext2_free_inode(uint32_t inode_num)`: Marks an inode as free.
    *   Handle the mapping of logical file blocks to physical disk blocks using direct, singly, doubly, and triply indirect block pointers within the inode structure.

### Phase 4.4: Block Management

*   **File**: `fs/ext2/ext2_block.c`.
*   **Purpose**: Manage the allocation and deallocation of data blocks on the disk.
*   **Action**: Implement functions for:
    *   `ext2_alloc_block()`: Finds and allocates a free data block using the block bitmap.
    *   `ext2_free_block(uint32_t block_num)`: Marks a data block as free.
    *   `ext2_read_block(uint32_t block_num, void *buffer)`: Reads a single data block into memory.
    *   `ext2_write_block(uint32_t block_num, const void *buffer)`: Writes a single data block to disk.

### Phase 4.5: Directory Management

*   **File**: `fs/ext2/ext2_dir.c`.
*   **Purpose**: Implement the hierarchical directory structure of Ext2.
*   **Action**: Implement functions for:
    *   `ext2_lookup(inode_t *parent_dir_inode, const char *name)`: Searches for a file or subdirectory entry within a given directory inode.
    *   `ext2_create_dir_entry(inode_t *parent_dir_inode, const char *name, uint32_t child_inode_num, uint8_t file_type)`: Adds a new entry to a directory.
    *   `ext2_read_dir(inode_t *dir_inode, uint32_t entry_offset, dir_entry_t *entry_buffer)`: Reads directory entries, allowing for directory listing.

### Phase 4.6: File Data Operations

*   **File**: `fs/ext2/ext2_file.c`.
*   **Purpose**: Implement the actual reading and writing of file data, leveraging inode and block management.
*   **Action**: Implement `ext2_read(inode_t *inode, void *buffer, size_t size, off_t offset)` and `ext2_write(inode_t *inode, const void *buffer, size_t size, off_t offset)`.
    *   These functions will use the inode's block pointers (direct and indirect) to determine the physical disk blocks corresponding to the requested file offset and then use the ATA driver to perform the actual data transfer.

### Phase 4.7: Ext2 File System Registration

*   **File**: `fs/ext2/ext2.c`.
*   **Action**: Create an `ext2_filesystem_t` structure that populates the function pointers required by the VFS (e.g., `open`, `read`, `write`, `mount`, `unmount`). Register this structure with the VFS using `vfs_register_filesystem`.

## Part 5: Layering Mechanism and Example Layers

This phase introduces the core concept of layering, where file system operations can be intercepted and modified by intermediate layers before reaching the base file system or the application. This is where the true flexibility of a layered architecture shines.

### Phase 5.1: Define Layer Interface

*   **File**: `include/vfs_layer.h` (new file).
*   **Purpose**: Create a generic interface for file system layers, similar to the VFS node operations. This interface defines the contract that all layers must adhere to.
*   **Action**: Define `struct vfs_layer_ops` with function pointers for all relevant file operations (e.g., `open`, `close`, `read`, `write`, `ioctl`, `stat`, `mkdir`, `rmdir`). Each function in a layer will typically perform its specific logic and then call the corresponding function in the layer immediately below it in the stack, passing the modified request or data.

### Phase 5.2: Implement Layer Stacking in VFS

*   **File**: `kernel/vfs.c`.
*   **Purpose**: Modify the VFS to dynamically support the stacking of multiple layers on top of a concrete file system.
*   **Action**: When a VFS operation (e.g., `vfs_open`) is invoked, instead of directly calling the concrete file system's function, the VFS should iterate through a linked list or array of registered layers associated with the target file or mount point. Each layer's function will be called in a predefined order (e.g., top-down). The `vfs_node` structure should be extended to include a pointer to the *topmost* active layer for that specific file or directory, allowing subsequent operations to correctly traverse the stack.

### Phase 5.3: Example Layer: Read-Only Layer

*   **File**: `fs/layers/ro_layer.c` (new directory and file).
*   **Purpose**: To demonstrate the layering mechanism by creating a simple layer that enforces read-only access on any file system mounted beneath it.
*   **Action**: Implement `ro_layer_ops`. For `read` operations, the request is simply passed down to the next layer. For `write`, `create`, `mkdir`, `rmdir`, or `unlink` operations, the layer intercepts the call and immediately returns an error (e.g., `EACCES` or `EROFS`), preventing any modifications to the underlying file system.

### Phase 5.4: Example Layer: Simple Caching Layer

*   **File**: `fs/layers/cache_layer.c`.
*   **Purpose**: To implement a basic block-level or file-level caching layer to significantly improve read performance by reducing disk I/O.
*   **Action**: Implement `cache_layer_ops`. For `read` operations, the layer first checks its internal cache. If the requested data is found (a cache hit), it is returned directly. If not (a cache miss), the request is passed down to the next layer, and the retrieved data is then stored in the cache before being returned. For `write` operations, a write-through or write-back policy can be implemented: write to cache and pass down immediately (write-through), or write to cache and defer writing to disk (write-back).

### Phase 5.5: Example Layer: Encryption/Decryption Layer

*   **File**: `fs/layers/crypto_layer.c`.
*   **Purpose**: To provide transparent encryption and decryption of file data.
*   **Action**: Implement `crypto_layer_ops`. On `write`, data passed from above is encrypted before being passed down to the next layer. On `read`, data received from the layer below is decrypted before being passed up. This layer would require integration with a kernel-level cryptography library.

## Part 6: Integration with System Calls and User-Space Exposure

This final phase seamlessly connects the layered file system to the system call interface, providing user-mode applications with full access to the enhanced file system functionalities.

### Phase 6.1: Implement File System System Calls

*   **File**: `kernel/syscall.c` or a dedicated `kernel/fs_syscalls.c`.
*   **Purpose**: To expose the rich functionalities of the layered file system to user-mode programs through a standardized system call interface.
*   **Action**: Implement the kernel service functions for all relevant file system system calls, including `SYS_OPEN`, `SYS_READ`, `SYS_WRITE`, `SYS_CLOSE`, `SYS_LSEEK`, `SYS_STAT`, `SYS_MKDIR`, `SYS_RMDIR`, `SYS_UNLINK`, `SYS_RENAME`, etc.
    *   Each of these system call handlers will act as a wrapper, calling the corresponding VFS function (e.g., `sys_open` will call `vfs_open`).
    *   Crucially, manage file descriptors (small integers returned by `open`) to track open files on a per-process basis. Each file descriptor will be associated with a specific `vfs_node` and its active stack of layers.

### Phase 6.2: User-Mode Library (Standard C Library)

*   **File**: `user/libc/stdio.c` and other related files (new directory and files).
*   **Purpose**: To provide a standard C library interface (e.g., POSIX-like functions) for file operations to user-mode programs. This abstracts away the raw system calls, making application development easier.
*   **Action**: Implement functions such as `fopen`, `fread`, `fwrite`, `fclose`, `opendir`, `readdir`, `stat`, etc. These library functions will internally make the appropriate system calls (e.g., `fopen` will translate to `SYS_OPEN`, `fread` to `SYS_READ`).

### Phase 6.3: User-Mode Test Programs

*   **File**: `user/test_fs.s` or `user/test_fs.c`.
*   **Purpose**: To thoroughly verify the entire layered file system stack, from the user application down through the VFS layers to the concrete file system and the disk driver.
*   **Action**: Develop a comprehensive suite of test programs that:
    *   Create, write to, and read from files, verifying data integrity across different layers.
    *   Create, list, and remove directories, testing hierarchical navigation and permissions.
    *   Test the specific functionalities of each implemented layer (e.g., attempt to write to a file on a read-only mounted layer and verify that the `EACCES` error is correctly returned).
    *   Perform operations on files that span multiple blocks and test seeking functionality.
    *   Test concurrent access to files from multiple processes to ensure proper synchronization and cache coherency.
